The content-derived scratch-slot embedding work (docs plan `smooth-noodling-kurzweil.md`, [[deterministic-mechanisms-thesis]]/[[scratch-tokens-context-translation-layer]] lineage) is COMPLETE, not a backlog item — committed across `0bc3a01` (mean-pool CPU scaffold), `e11e0da` (training integration: `train_batch` threads per-window `ScratchBindings`), `eb9feee`+`b7896ab` (CharEncoder arm + training), `a40927e` (Scalar arm, the scalar-reentry encoding). `tests/scratch_embed_tests.cpp` covers all of it.

**The finding (from b7896ab's commit, VERIFIED against the actual commit message 2026-07-16 — corrects an earlier mischaracterization in this file): the probe fixed was the ORDER-AGNOSTIC "contains X" task (#4b, `content_contains_task`), not the order-SENSITIVE "starts with X" task (#4, `content_select_task`) — the commit message says so explicitly: "FINDING (d128, order-agnostic 'contains X')". Mean-pool = 0.325 (chance ~0.333, i.e. at chance); AdamW-trained CharEncoder = 0.392 (modest but real lift above chance and above plain mean-pool).**

**Why CharEncoder is NOT actually order-sensitive (this file previously claimed it was — wrong):** CharEncoder is `out = Σ_f relu(W · e_f)` — a SHARED weight `W` applied per-fragment, then SUMMED. By the Deep Sets theorem (Zaheer et al. 2017, NeurIPS, "Deep Sets" — `f(S) = ρ(Σ_{s∈S} φ(s))` is the canonical/necessary form for any permutation-INVARIANT set function), this is PROVABLY permutation-invariant: reordering the fragments cannot change the sum, exactly like MeanPool. CharEncoder's real lever is a better per-fragment nonlinear transform (relu creates sparser, less mutually-cancelling per-channel "detector" activations than a linear average), which helps PRESENCE/set discrimination ("is character X anywhere in this OOV") but mathematically cannot carry positional information ("is X the FIRST character") — no amount of training changes this, it is a representational ceiling, not a capacity problem. This is also consistent with `scratchspike.hpp`'s own production curriculum choice: it deliberately ships #4b (order-agnostic contains, via LOCAL-GROUNDED CoT that RESOLVES each slot's real bytes into the stream, not via content-derived embeddings at all) and explicitly EXCLUDES #4 (starts-with) as "not learnable model-side at this scale."

**How to apply:** MeanPool and CharEncoder are both bag-of-fragments (permutation-invariant) representations — fine for a use case that only needs "does this slot's content contain/relate to X" (presence/identity), PROVABLY insufficient for any use case needing "WHICH position" (order-sensitive) — see [[meanpool-alternatives-prior-art-and-math]] for the full survey and candidate ranking.

**Updated 2026-07-16 (same day, later): the top candidate is now BUILT, and a real-but-modest/noisy effect is confirmed across seeds.** `SlotEncoding::Hash` (RoPE-style positional binding — rotate each fragment by its position, then sum; zero new params) is implemented, gradient-checked, and confirmed genuinely order-sensitive by direct test (commit `7daa65f`). A/B spike on `content_select_task` (#4, "starts with X" — the exact probe excluded from production because nothing beat chance): first single run looked strong (MeanPool held-out 0.375, Hash 0.450), but a 3-seed follow-up tempered that — mean held-out MeanPool 0.356, Hash 0.403 (chance 0.333), with one seed showing BOTH arms collapse to an identical degenerate output (no gap at all that seed) and the other two showing a clear Hash win. Directionally consistent (Hash never underperforms MeanPool) but not statistically decisive at n=3 (paired t≈2.0, df=2). Worth remembering: this isn't the only route to positional reasoning — combine/uncombine's resolve-then-attend mechanism already answers these queries (at the cost of a multi-step trace); a working one-hop encoder's payoff is a shortcut instead.

**Updated 2026-07-16 (same day, later still): Candidate 3 (ConvPool, char-CNN style) is STRONGER than Hash.** `SlotEncoding::ConvPool` (a learned width-2 convolution + relu + maxpool over consecutive fragment pairs, reusing CharEncoder's own `enc_w`/`enc_w_grad` pointers as a `[2,C,C]` buffer) is implemented, gradient-checked, and order-sensitive by direct test. Multi-seeded A/B from the start (baseline = fully plain, no content-embed at all, matching CharEncoder's own methodology): mean held-out plain 0.344 (at chance 0.333, as expected), ConvPool **0.458** (gap +0.114, roughly 2.4x Hash's own gap) — and ConvPool wins on EVERY seed, no ties or degenerate-collapse failures the way Hash's seed 2 showed.

**Updated 2026-07-16 (same day, later still again): Candidate 2 (HRR, circular-convolution binding) is DECISIVELY stronger than both, and is now the clear leading candidate.** `SlotEncoding::HRR` (Plate 1995 -- bind each fragment to a fixed pseudo-random per-position role vector via circular convolution, then sum; NO learned params, unlike ConvPool) is implemented, gradient-checked, order-sensitive by direct test. Multi-seeded A/B (baseline MeanPool): mean held-out MeanPool 0.356, HRR **0.744** -- more than double chance (0.333), strong and consistent across all 3 seeds, held-out tracking drilled closely in every seed (genuine generalization). This gap (+0.388) is ~3.4x ConvPool's and ~8x Hash's -- not incremental, qualitatively different. Learned params turned out NOT to be the deciding factor (HRR has none and wins by far the largest margin) -- the quasi-orthogonality of independent random high-dimensional role vectors (the classic VSA property) gives HRR much less cross-position interference than Hash's low-rank pairwise rotation or ConvPool's locally-windowed view. Because HRR needs no learned params, it does NOT depend on [[slot-encoder-checkpoint-persistence-design]] the way ConvPool/CharEncoder do. Full detail (including per-seed numbers) in [[meanpool-alternatives-prior-art-and-math]]'s RESULT sections.

Reviewed via `/cpp-review` before commit (consolidated a duplicated switch statement, hoisted a per-window lookup to once-per-run). Verified with a real train+gen smoke run (d196, `--scratch-mix 0.3 --content-embed`): train log `content-derived scratch embeddings ON (hrr, CPU-forced)`, `config.json` shows `content_embed_kind: "hrr"`, gen log shows `content-embed hrr` -- loop closed correctly. Hash and ConvPool remain implemented but unwired (ConvPool still needs [[slot-encoder-checkpoint-persistence-design]]'s param-layout work first).

**Updated 2026-07-16: gen-time wiring is now DONE too**, and for BOTH curricula. `751240e` wired `train_stage.cpp`'s `train_batch` + `gen_stage.cpp`'s `set_scratch_bindings` for `--scratch-mix` (content_embed_active required `scratch_mix>0 && op_mix<=0` at first, since `--op-mix`'s collapsed results were computed then discarded — no `doc_bindings` table existed for it). So `--content-embed` now works from `--scratch-mix` alone, `--op-mix` alone, or both blended.
