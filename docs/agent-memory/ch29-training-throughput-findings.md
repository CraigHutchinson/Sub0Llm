Hard-won, measurement-driven findings for ch29 diffusion training throughput (small model: V=512, D=128, 4–8 layers, ~1.6M params, seq_len=64) on the [[host-cpu-arrow-lake-hx]] (8 P-cores). Use the `ch29b_diffusion_training` probes (`--affinity-test`, `--alloc-probe`, `--gemm-probe`, `--batch-bench`, `--profile-batch`, `--alloc-count [--alloc-batch B] [--founded]`).

**UPDATE 2026-06-17 — FOUNDED arch (D=256/L6, ~6M params), post pool-thrash fix.** The "bandwidth root cause / W≈4 optimal" conclusion below was for the TINY D=128 model (low compute/byte → bus-bound). The FOUNDED default is more compute-bound (`--founded` sweep: 87–93% compute) and behaves differently. (1) TensorPool was THRASHING at founded scale: its fixed 16 MB/class cap (tuned for D=128) was too small, measured 242 free+realloc per per-worker step (B=2) via `--alloc-count --founded`. Fixed with a SELF-SCALING high-water-mark cap (no magic number — see [[derive-bounds-from-scale-not-fixed-thresholds]]); 242→16 (~90% cut). BlockPool was already clean (0). (2) That allocator-lock contention was what capped W>8 on the old binary: post-fix `--founded` best-of-3 bench scales W=8 92.6 → W=14 116 → W=20 129 w/s. (3) BUT sustained real training at W=16/B=16 settles only ~101 w/s (not the bench's 111) — the barrier is gated by the slowest worker and an E-core doing 1 window ≈ a P-core doing 2, so heterogeneous P+E scaling for a balanced batch is only single-digit-% over W=8 (~92–100). Live run resumed at W=16 (full cores, marginally faster, identical B=16 gradient) from ckpt 179760. FOLLOW-UP lever for real full-core gain: heterogeneous-aware split (give P-cores MORE windows than E-cores so finish times match) — the barrier loss, not bandwidth, is now the cap at this model size. W≈4-being-optimal does NOT hold for founded.

**Per-window forward+backward ≈ 10 ms is ~85% compute, ~15% overhead** — NOT autograd/alloc-overhead-bound as first assumed. Proven because batching B windows into one graph gave only **+15%** (`--batch-bench`), not the predicted 3–8×.

**RE-MEASURED 2026-06-15 (user hunch — the old +15% was pre-zero-alloc-work / may have been heap-confounded): the single-thread batched win is now ~+39%, NOT +15%.** `--batch-bench` single-thread (E-core 14, uncontended): serial 50.5 win/s → **batched B=8 70.2 win/s (+39%)**; sweet spot B=8 (B=16/32/64 ~+30%, diminishing); B=4 only +4%. `--alloc-count` shows a per-window step STILL does **5797 heap allocs/step (519 KB)** (after the SmallVector 62% cut), so it IS partly heap-bound — and a batched B-window step is ONE autograd graph ≈ same ~5797 allocs total ⇒ ~B× fewer allocs/window, which the batched throughput recovers. ACTIONABLE: (1) wire `--batch B` into the SINGLE-THREAD training path (free +39% + B-window variance reduction — pairs with the [[ch31-diffusion-optimization-sandbox-plan]] variance findings); (2) RE-TEST per-worker batching in the THREADED ParallelTrainer (the old "batched+threaded-GEMM worse" was about threading the GEMMs AND may also have been alloc-confounded — per-worker batching ≠ that); (3) the remaining 5797 allocs/step (shared_ptr control blocks per Tensor + Edge std::function VJP closures) still hurt BOTH paths — reducing them helps everything.

**What parallelizes (verified):**
- Pure compute: pool scales **6.5–7.7×** on 8 P-cores (`--profile-batch` pool sanity).
- A single GEMM's M-rows: **4.2× @8, 6× @12** (`--gemm-probe`). No memory-bandwidth wall at these sizes.
- Per-window data parallelism (ParallelTrainer, 1 window/worker) parallelizes the WHOLE step → **~2.5× peak (W=5, ~255 win/s)**, capped by global-heap **allocator-lock convoy** (12% CPU at 21 threads; pure-alloc probe tops out ~4.8×).

**What does NOT help (verified, against intuition):**
- Threading just the GEMMs in a batched forward+backward → **~100 win/s (WORSE than per-window's 255)**. Forward threads great (260 win/s) but the **backward is the wall (~6 ms/window)** and is dominated by NON-GEMM serial scalar work (softmax/rope/rmsnorm/elementwise backward + graph traversal + grad accumulation), which GEMM threading can't touch. So softmax/CE is NOT the bottleneck either (`--profile-batch`: sum-loss ≈ CE-loss).

**Conclusion / direction:** the throughput prize is parallelizing the *whole* step, which per-window already does — the lever is **removing its allocator cap (zero-alloc / thread-caching allocator)**, vindicating the original instinct. Batched+threaded-GEMM is a worse near-term path (only ~40% of work threads); keep the batched code as a tested foundation for CUDA and for an eventual fully-threaded-backward, not as the CPU win.

**Zero-alloc substrate (measure, don't guess — `--alloc-count` in ch29b counts heap allocs/step):** a per-window step did **15,175 heap allocs/step, 78% ≤32 bytes** — dominated by every Tensor's shape/stride `std::vector`. Fix = `SmallVector<int64,4>` inline storage behind `Tensor::Shape`/`Strides` (`include/sub0llm/core/small_vector.hpp`); the aliases insulated all callers (only 3 sites needed fixing). Result: **15,175 → 5,797 allocs/step (−62%)**, 519+9 tests green. Remaining offenders (next targets): the two shared_ptr control blocks per Tensor (Storage make_shared + pooled-buffer `shared_ptr<byte[]>` deleter block) and the `Edge` `std::function` VJP closures (SBO callable). `Workspace` (`core/workspace.hpp`) is the preallocated bump-arena backbone for a future fully-static path.

**DEFINITIVE ROOT CAUSE (confirmed, not inferred): memory bandwidth.** `bench_membw` shows read bandwidth itself scales only **1t 32 GB/s → 4t 64 (2.0×) → 8t 75 (2.4×)** — one P-core already pulls a third of the bus, so it saturates by ~4–8 cores. Per-window training scales **2.5×**, a near-exact match. So ~2.5× IS the hardware ceiling for this tiny (D=128, 1.6M-param) model: it has low compute-per-byte, so 8 workers streaming f32 activations/grads saturate DRAM. Proof it's NOT the allocator: cutting allocs 62% (SmallVector) left scaling unchanged. NOT batching (+15%, same bytes/window). NOT GEMM threading (helps the cache-resident forward GEMMs, not the bandwidth-bound elementwise backward). The plateau-flat-across-W=3..8 shape is the saturation signature. **Optimal config = W≈4** (best bandwidth efficiency before the wall; W=8 is no faster and burns 4 extra cores). The only levers past 2.5× move FEWER BYTES (bf16/f16 activations, op fusion to keep activations in cache) or move to GPU (higher compute/byte) — and GPU only pays once the model grows ~10× (per [[ch27-gpu-forward-build-arc]] crossover). We are AT the [[optimization-target-is-hardware-ceiling]] for this model on this CPU.

**`--pin` policy shipped + validated (2026-06-14):** `cpu_topology::resolve_pin_set` (shared, unit-tested) + ch29 `--pin auto|all|P|E|"lo-hi"|"a,b,c"` → `ParallelTrainer` pin override. Lets CONCURRENT training jobs take DISJOINT cores. Validated: running two trainers oversubscribing the SAME P-cores collapsed each to ~10 win/s (the ~30× multi-job slowdown was core oversubscription, NOT just the bus); pinning them to disjoint P-core sets ([0,1,10,11] vs [12,13,22,23]) let both progress — the proxy hit ~65 win/s concurrently. Promote the gemma-local `parse_cpu_list`/`resolve_cores` to the shared one too (DRY backlog). Also added `setvbuf(stdout,_IONBF)` to ch29 main so redirected logs are live-monitorable (Windows _IOLBF degrades to full-buffering — the block-buffered "empty log" trap).

**OPEN throughput observation (needs an isolated bench, don't overclaim):** REAL full-training (full forward+backward+clip+Adam+periodic eval) measured FAR below the old probe "~255 win/s peak": full-corpus undertrain (2.19M-token stream, W=4, --track-recall) ≈ **14 win/s**, the 136K-token proxy (W=4, frequent evals) ≈ **65 win/s** — both well under 255. Candidate causes, UNattributed: (a) corpus-size cache effect — the random-offset window GATHER over an 8.7MB train stream spills L2→L3/DRAM and competes with the bandwidth-bound activation traffic (proxy's 0.5MB stream is L2-resident); (b) eval-frequency drag (the small-corpus proxy evals every ~531 steps vs the full corpus every ~4280, yet the proxy is still FASTER → makes (a) look real, even understated); (c) the old 255 was a pure-compute probe (`--profile-batch`), not full real-training with optimizer/eval. NEEDS: a fixed-step, eval-off, single-job run at each corpus size to attribute. Candidate fix if (a) dominates: locality-batched offsets (draw each step's W windows from a rotating L2-sized shard of the stream instead of fully-random over the whole corpus) — preserves epoch-level randomness, keeps per-step gather L2-local.

**Affinity is fine** (proven: 24/24 workers stay pinned, 0% off-pin) — never the cause. Pin via [[cpu-threading-model]]. Thread-disjoint matmul row-threading is bitwise-identical; matmul_tb M-partition+reduce reorders floats (~1e-6), gated to M≥256 so small unit tests stay exact. Intra-op matmul threading and per-window data parallelism CONFLICT (W×8 oversubscription) — `intra_op_threading_enabled()` thread-local opt-out keeps ParallelTrainer workers serial.
