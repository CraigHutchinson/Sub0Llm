Standing up the d768/L16/v32872 FineWeb-Edu native (GPU) build hit four Windows/scale traps, all now fixed + committed (this session, branch claude/llm-transformers-1bit-qf3t3i):

**1. Static-arena SizeOfImage limit → 0xC000007B (committed d2cff68).** The four SHARED CPU arenas in backend_cpu.cpp (`g_param_data/grad/m/vel`) were `static std::array<float, PARAM_FLOATS>`. At d768 that is 4×164M×4 = **2.6 GB of zero-init BSS**, which pushes sub0_core.dll's PE `SizeOfImage` past what the Windows loader will map → EVERY native binary fails to start with `STATUS_INVALID_IMAGE_FORMAT` (0xC000007B), before main. Fix: heap-allocate via `unique_ptr<float[]>` + `ensure_shared_params()` (call_once), keeping `[]`/`.get()` access. The per-thread Worker arrays were ALREADY heap for this exact reason (see the comment block in backend_cpu.cpp); the shared arenas were the miss. **Diagnostic that cracked it: `dumpbin /headers <dll> | findstr "size of image"` — native .data was 0x9CA446A8 (~2.6GB) vs ts_gpu ~70MB.** LoadLibraryEx per-DLL (err 193 = ERROR_BAD_EXE_FORMAT) isolated sub0_core.dll; imports/manifest/flags were all identical to the working ts_gpu build, so it was pure image size. Rule: any storage sized by a compile-time config constant (PARAM_FLOATS, ACT_CAP, VOCAB×…) must be HEAP, never a file-scope/static array — see [[derive-bounds-from-scale-not-fixed-thresholds]].

**2. `ninja -t clean <target>` CASCADES into the generated config → full re-tokenize.** sub0_core transitively depends on the auto-configure custom command (generated headers), so `ninja -t clean sub0_core` deleted `sub0_config.hpp`/`tokenizer.bin` (and tried corpus.tok, which was locked), and the next build re-ran sub0llm-configure = **re-tokenized the 46GB corpus** (~fast via the `<corpus>.words` scan cache, but still minutes + rewrites the 25GB corpus.tok). NEVER `ninja -t clean` an engine target. To force a clean recompile of one TU, delete just its `.obj` under `CMakeFiles/<target>.dir/` and rebuild — that does NOT touch the generated config.

**2b. CORRECTION (2026-07-02) — the "relinking sub0llm-configure.exe triggers it" claim above was WRONG / incomplete.** While a train was LIVE on `native` (holding its DLLs + `corpus.tok` open), a plain, targeted ninja build of ONE unrelated `.obj` file (`ninja out/build/native tests/CMakeFiles/sub0_tests.dir/cuda_tests.cpp.obj` — no `-t clean`, no touching the configurator, no touching the generated config) STILL cascaded into a full auto-configure re-run: 91s of 24-thread unigram relearn, then `configure error: cannot write '...corpus.tok'` (blocked only because the running train's mmap held the file locked — pure luck, not a design safeguard; on a build dir with NO live lock this would have silently succeeded and clobbered `corpus.tok` out from under the train). Root cause not fully isolated (ninja's dependency check for the auto-configure custom command output appears to trigger on ANY build invocation in the directory under some condition broader than "relinked the configurator" or "deleted an output" — possibly a timestamp artifact from an earlier stash/pop A-B test in the same session). **Rule, revised: while a train (or anything else) is running against a build dir's binaries, do NOT invoke `cmake --build` / `ninja` against that SAME build dir AT ALL — not even a single, unrelated `.obj` target — until the process is stopped.** If you need to compile/verify CUDA source changes while a train is live, use a **standalone `nvcc -c <file> -o scratch.obj`** invocation outside the CMake/ninja graph entirely (see the `ptxas -v` register-audit recipe in [[attention-kernel-throughput-bottleneck]]) — that bypasses the auto-configure dependency graph completely and is safe. Full link + test still requires the build dir to be free.

**3. Running the native GPU exe needs the right PATH.** `sub0_core.dll` imports `libomp140.x86_64.dll` (found in **C:\Windows\System32**, the good release copy — do NOT copy the VS `debug_nonredist` one, it demands the debug CRT SxS and itself fails 0xC000007B). CUDA 13.2 runtime DLLs (cudart/cublas/cublasLt _13) live in **`CUDA\v13.2\bin\x64`** (not `bin`). So a detached launch must prepend `<build>;<CUDA>\bin\x64;<CUDA>\bin` to PATH. ts_gpu binaries load in the bare tool env because their arenas fit; native only differed by image size (trap 1).

**4. epoch_steps 32-bit overflow (committed 1aa4bdb).** train_stage cast `est_train_tokens` (size_t, 12 B) to `long` (32-bit on LLP64 Windows) → wrapped negative → epoch_steps=1 → run stopped after 30 STEPS and evaluated every step. Compute in size_t, then narrow. See [[configurator-ingest-optimization]] (same `long`-is-32-bit trap the configurator already fixed).

**FOLLOW-UP from the self-review (not yet fixed — needs an engine rebuild, blocked while the train holds the DLLs):** `ensure_shared_params()` uses `make_unique<float[]>` which value-initializes (zeroes) ALL FOUR arenas, touching every page → for a large-model *inference* run (gen/eval) it now commits ~2 GB for grad/m/vel that inference never uses (the old static BSS was demand-zero, stayed uncommitted). No effect on training (uses all four) or small configs. Fix when convenient: allocate only `g_param_data` for inference and defer grad/m/vel to the first training step (or `VirtualAlloc` demand-zero without the value-init touch). Also a known edge (inherent, low priority): resuming a model AFTER reconfiguring to a different SAME-SIZE vocab re-bundles + re-stamps the new tokenizer, so the fingerprint guard won't catch that weights↔vocab drift (the checkpoint dim-check catches vocab-SIZE changes).

**Crash-resistance checkpoint (committed 77b2acb):** eval-only checkpointing left a ~20h gap at FineWeb's eval cadence; added a `CKPT_SECONDS=3600` wall-clock tick that saves between evals (resets when an eval checkpoints). Bounds crash loss to ~1h.

**Launch env recipe (detached, PowerShell):** `$env:PATH = "<build>;<CUDA v13.2>\bin\x64;<CUDA v13.2>\bin;$env:PATH"` then `Start-Process sub0llm-train.exe --keep 5 -WorkingDirectory <build> -RedirectStandardOutput ... -WindowStyle Hidden`. Resume is automatic from the latest checkpoint. Rebuilding the engine requires STOPPING the train first (it locks native's DLLs) -- and per 2b above, this means NO ninja/cmake build in that dir at all, not just avoiding a configurator relink.

**FineWeb-Edu train is LIVE (2026-07-02):** models/sub0llm_fineweb_edu_d768l16h8sq512v32872r_e226d64, GPU sm_120 (7.3/8.1 GB VRAM, 100% util), 12.6B tokens (11.99B train), 164M params, 780602 steps/epoch, eval every 78060 (~first eval + checkpoint hours out), heartbeat every 180s, --keep 5, plateau-stopped. Launch PATH recipe above. See [[gen-decode-kv-cache-optimization]] for the tokenizer-bundling/fingerprint work also shipped this session.

**5. RESOLVED — the 2b near-miss's root fix (committed fcea638): pin corpus.tok + tokenizer into the model dir, not just avoid touching the build dir.** Rather than relying on discipline ("never build while a train runs"), training now HARDLINKS corpus.tok + tokenizer.tok into the model directory before reading either (`bundle_into_model_dir` in train_stage.cpp; falls back to a real copy only under a size threshold — correct even for a 25GB corpus.tok since a hardlink is near-instant/zero-disk). This REQUIRES the configurator to publish both files via tmp-file + atomic rename (not a direct truncate-open at the final path) — a rename repoints only the build tree's directory entry, leaving the model's hardlinked pin pointing at the OLD data untouched; an in-place truncate would have corrupted every hardlink alike. **Verified end-to-end with `fsutil file queryfileid`:** pinned copy shares the build tree's exact NTFS file ID right after training starts (true hardlink, not a copy); after a REAL `configure` re-run against the live build dir, the pinned copy's file ID was UNCHANGED while the build tree's got a new one. A model's training run is now provably immune to a reconfigure happening underneath it — the 2b workaround (never build in a locked dir) is now a secondary safety net, not the only one. NOTE: hardlinks require same-VOLUME; the fallback-to-copy path was confirmed via a cross-drive test (C: scratch vs D: project) — silently falls back correctly, just costs real disk/time for a huge corpus if the model dir ever ends up on a different drive than the build tree.

**5b. Also fixed in the same pass: `model_out` (an explicit --out path) never called `create_directories`.** Only the auto-derived model-dir branch did, so `sub0::log::set_file` (train.log) silently failed to open whenever an explicit target directory didn't exist yet — a PRE-EXISTING bug, newly exposed because the pinning logic has the same requirement. Both branches now ensure the directory exists before train.log/pinning touch it.

**6. Renamed tokenizer.bin -> tokenizer.tok (committed fcea638, user-requested)** so it visually pairs with corpus.tok as the tokenizer's two matched, versioned outputs. `default_tokenizer()`/`load_tokenizer()` etc. keep their accurate "tokenizer" naming — only the file extension changed. Mechanical rename across configurator emission, gen/train's bundled-copy lookups, comments, docs, tests.
