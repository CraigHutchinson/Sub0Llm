## 1. Scratch tokens / packing / KV-trace memoization -- the active thread, richest findings

**Where this landed**: axis 9 (attention-capacity preservation) root-caused, not just poked at, AND a
real O(1)-cost positive found. Four convergent findings: (a) compression capacity is the bottleneck, not
information availability (candidate 1's richer-input swap didn't help; Phase H's marker-add to
A/candidate-1 made them WORSE); (b) no-compression splice (candidate 2) is provably EXACT once
`SPELL_START`/`SPELL_END` markers are included (1.000 cos_sim, zero exceptions, 9/9 subjects); (c) an
isolated-captured trace, WITH markers, reused in a genuinely different real context still hits ~0.98
cos_sim -- context-sensitivity costs less than marker omission does; (d) **Phase I: periodic packed-
content re-injection (Nanbeige-inspired, zero learned params, EVAL-ONLY) lifts accuracy 3/9->5/9 and mean
cos_sim 0.83->0.86 at O(1) cost** -- the first mechanism in this whole thread to show a real positive
without paying candidate 2's O(n) cost or losing to candidate 1/mechanism A's compression bottleneck. Full
story: [[factspike-piece-transfer-validated]], `docs/FACTSPIKE.md` (Phase A-I), `docs/SCRATCH_TOKEN_FRAMING.md`
(the criteria-first requirements doc, axis table + "candidate 3" fully updated).

**Concrete next steps, prioritized**:
1. **Wire periodic re-injection into the TRAINING graph** (Phase I's own natural follow-up, NOT YET
   STARTED -- the current spike is eval-only, `forward_one`-only; `Model::forward()`/`train_batch` is a
   structurally separate autodiff implementation with zero awareness of this mechanism). A LEARNED gate
   (matching Nanbeige's own `NanbeigeNgramLayerFusion` design -- normalize both sides, gate via a learned
   dot-product, project the injected value through a learned matrix) rather than Phase I's flat
   fraction-of-norm heuristic is the natural next increment, now genuinely justified by a real eval-only
   positive rather than speculative. This is the single most promising concrete next step in the whole
   scratch-token thread as of this note.
2. **Marker-inclusive retest of candidate 1's own pooling operator swap** was NOT tried -- Phase H only
   retested mechanism A and candidate-1-as-originally-specified with markers. A DIFFERENT pooling operator
   (not HRR) fed marker-inclusive input hasn't been tested at all -- HRR's own fixed-capacity bundle was
   isolated as the bottleneck (Phase G), but no alternative operator has been tried yet.
3. **Concatenated n-gram-style compression** ([[nanbeige-architecture-reference]]): a verified, real,
   shipping alternative to HRR's bind-by-role -- concatenate pieces with zero interference, THEN a single
   learned linear projects down to `D_MODEL`. Untried. Needs new learned parameters (reopens the
   checkpoint-persistence gap CharEncoder/ConvPool already have -- see #4 below).
4. **HRR-crosstalk analytical cross-check** -- cheap, no training needed: fit the existing 9-point
   `(n_pieces, cos_sim)` dataset against Plate's `1/sqrt(n)` bundling-fidelity curve. Says whether the
   observed degradation is "textbook HRR crosstalk, nothing more" or something beyond that. Still not
   done as of this note, despite being flagged repeatedly.
5. **Polysemy / semantic context-sensitivity is completely untested.** Everything measured so far (F/G's
   0.98) used invented proper nouns with zero polysemy by construction -- structurally cannot speak to
   whether memoizing a genuinely ambiguous word's trace (bank/spring/lead) would misfire when spliced into
   a context implying a different sense. This is architecturally a much bigger risk than anything measured
   -- a dedicated experiment (capture one sense's context, splice into a context implying the other,
   check for confusion) would need to exist before claiming this generalizes past low-polysemy vocabulary
   (rare/technical terms, names -- which is what scratch tokens have always targeted anyway, likely not
   coincidentally).
6. **`corpus_collapse` production retest, IF any axis-9 fix validates at toy scale first.** The existing
   marker-inclusive retest at real TinyStories scale showed NO NELBO effect (`docs/CORPUS_COLLAPSE.md`'s
   2026-07-21 entry) -- a real negative at that coarse metric, but re-testing whatever DOES validate
   cleanly at factspike toy-scale (once axis 9 has a real fix, not just the marker fix which didn't help
   compression-based mechanisms) is the natural production-relevance gate.
7. **Checkpoint persistence for any learned compression operator** -- CharEncoder/ConvPool already have
   this exact gap (`TODO(charencoder-production)`, [[slot-encoder-checkpoint-persistence-design]]). Any
   spike involving new learned parameters (per-layer fusion gates, concat-then-project) inherits this
   blocker before reaching production regardless of how well it performs.

## 3. Correctness / test infra gaps

- **`engine_tests` gradient-check fails at production dims** (d448/L11/H7) but passes at tiny dims --
  root cause not investigated, real correctness question left open.
  [[engine-tests-gradient-check-dims-dependent]]
- **`loss_mask_tests.cpp`'s masked finite-difference check passes only by accident** (characterized
  2026-07-26 during the GQA work; NOT fixed -- deliberately left alone rather than reshaped as a side
  effect of an unrelated feature). Two compounding defects, both pre-existing on trunk:
  1. It never calls `reset_opt_state()`, so it inherits whatever global AdamW momentum earlier
     TEST_CASEs left behind -- the same hazard [[cross-test-optimizer-state-contamination]] documents
     and fixed in the spike tests. Its trajectory, and therefore where it takes the finite difference,
     is test-ORDER dependent. It passes in full-suite order and **fails standalone on unmodified
     trunk** (numeric=1.406 vs ||g||=1.172, +20%, tolerance 5%).
  2. Even with the optimizer state zeroed, the 5% tolerance is not achievable at d96/L8/H2. Measured
     eps sweep at a fixed clean point: 1e-2 -> 1.406, 3e-3 -> 1.114, 1e-3 -> 1.109, 3e-4 -> 1.109. It
     CONVERGES (so the residual is not curvature truncation) to ~5.4% below ||g||. The floor is float32
     quantization: ||g|| is spread over ~740k parameters, so most per-element displacements
     `eps*(g_i/||g||)` fall below a float32 ulp of the parameter and simply don't move, biasing the
     numeric derivative down. Large eps overshoots via curvature, small eps undershoots via
     quantization; there is no eps at which 5% is reachable here.

  at 1 KV head lands at 16% off. **This is not evidence of a gradient bug** -- `engine_tests`' own
  check passes under the same config, and its per-parameter probes perturb ONE parameter at a time
  (well clear of the ulp floor), which is the diagnostic that actually localizes a wrong backward.
  Proper fix: probe only the top-K largest-gradient parameters, where the displacement is numerically
  meaningful, instead of spreading ||g|| across all 740k.

## 7. C++23 modernisation: finish the `std::mdspan` adoption (added 2026-07-26)

The CPU backend ALREADY uses `std::mdspan` -- `src/backend_cpu.cpp:201` is
`using Mat = std::mdspan<float, std::dextents<std::size_t, 2>>;`, with `mat(span, rows, cols)` at `:202`
as the factory, used throughout `backward_node` (`ng[i, off + a]` etc. -- C++23 multidimensional
`operator[]`). This is NOT a "should we adopt mdspan" question; adoption happened. What remains is that
the adoption is partial, so two indexing idioms coexist:

- **`KVCache` (`backend_cpu.cpp:918-927`) is the clearest candidate.** It is a genuine 3-D
  `[N_LAYERS][SEQ_LEN][D_MODEL]` structure expressed as a flat `std::vector<float>` plus hand-rolled
  stride arithmetic in `krow(l,pos)`/`vrow(l,pos)`. A `std::mdspan` with STATIC extents
  (`std::extents<std::size_t, N_LAYERS, SEQ_LEN, D_MODEL>` -- all three are compile-time constants)
  would let the compiler fold the stride math and would make the layout self-documenting. Worth doing
  as its own change, NOT folded into a feature: the GQA and LoopSplit work both reshape this exact
  struct (KV row stride becomes `C_KV`; slots become per-execution rather than per-layer), so
  attempting both at once would entangle a mechanical refactor with a semantic change and make any
  resulting numerical drift ambiguous. Sequence it AFTER those land.
- Remaining manual `off + aa` pointer arithmetic inside `forward_one`'s attention loop
  (`backend_cpu.cpp:1176-1194`) -- lower value, hot path, measure before touching (`AGENTS.md` §1).
- CUDA (`backend_cuda.cu`) is out of scope: device code can't use `std::mdspan`.

Verification for any such change is already built: `tests/arch_identity_tests.cpp`'s fingerprints must
be BIT-IDENTICAL across a pure refactor (that is precisely what a mechanical re-expression should
guarantee), which is a stronger gate than the tolerance-based tests provide.

## 7d. Corpus SUBSET as a training config setting (added 2026-07-28, user request)

`fineweb_smoke.txt` (a 1.07 GB prefix of fineweb_edu) has been DELETED. A prefix-file was always the
wrong shape for "train on less": it is a second 1 GB artifact to keep in sync, and a prefix is a
biased sample -- fineweb_edu is not shuffled, so the first 25% is not 25% of the distribution.

**Replace it with a subset FRACTION in the training config**, and make the subset *distributed*, not a
prefix. This is an extension of the existing window sampler: the sampler already draws windows across
the corpus; a subset run simply draws from a deterministic, seed-stable, document-aligned subset of
the corpus rather than all of it. Document-aligned matters -- see the `<|endoftext|>` work; a subset
that cuts mid-document reintroduces exactly the boundary unsoundness just removed.

**Synergy with blend.hpp**: this is close to what the weighted blender already does, but along a
different axis. Blending mixes MULTIPLE sources at chosen proportions; subsetting takes a fraction of
ONE source while preserving its distribution. Check whether the blend scheduler's per-source
deficit/weighted-fair machinery can express "source X, 25% coverage" directly before adding a
parallel mechanism -- if it can, this is a config row, not a new subsystem.

Other use-cases beyond fast smoke runs, worth designing for rather than retrofitting:
- **Fair-cost A/B**: hold the token budget fixed while varying architecture, without the confound of
  a differently-shaped corpus prefix.
- **Learning-curve / scaling studies**: the same corpus at 10/25/50/100% is exactly the x-axis for
  "is the corpus or the parameter count the ceiling" -- the open question from
  [[tinystories-sweep-saturation]] and [[model-sizing-levers-from-corpus-stats]].
- **Held-out-by-construction eval**: a complementary subset (the 75% NOT trained on) is a genuinely
  unseen eval set from the same distribution, stronger than the current tail split.
- **Deterministic repro**: seed + fraction reproduces a run exactly without shipping a corpus file.

## 7f. Evaluation metrics: NELBO alone cannot resolve an architecture A/B (added 2026-07-28)

`val_nelbo` is a MEAN over all held-out tokens and is dominated by the frequent, easy ones. Two arms
can sit within seed noise of each other on mean NELBO while differing sharply on the hard tail --
which is exactly where a capacity claim like LoopSplit's would show. Given GQA's seed noise already
ran **1.73x the signal**, there is a real risk the current metric set **cannot resolve the LoopSplit
result even if the effect is real**. Prior art names the same failure: validation perplexity
"confounds stylistic mimicry with genuine factual internalization" (the Knowledge Retention Test,
arXiv 2601.03505), which is why corpus-grounded probes exist.

External suites (GSM8K, HellaSwag, MMLU) are useless at this scale -- a ~10M-param model sits at
chance -- so corpus-grounded metrics are the right family.

**Extend `sub0llm report`, do NOT add a new tool.** It already loads corpus.tok, computes the same
held-out split training uses, loads the model.bin offline, and already reports bits-per-byte
(`val_nelbo / (ln2 * bytes_per_tok)`). The work is contained to `compute_raw_metrics`: retain
per-token losses instead of only accumulating a mean, then bucket them.

1. **Frequency-stratified NELBO** -- bucket held-out tokens by training frequency (deciles), report
   NELBO per bucket. Highest value, nearly free. Capacity differences live in the rare tail.
2. **Position-stratified NELBO** -- bands 0-64 ... 448-512. The direct test of whether looping/depth
   helps LONG-RANGE structure, which is the actual hypothesis. Only meaningful with
   `SUB0_FIXED_SEQ=1`; under the default vary_seq, position 500 trains on 2.7% of steps.
3. **Corpus-grounded cloze probe** -- mask the final content word of factual sentences from held-out
   Cosmopedia docs, score top-1/top-5. Cosmopedia is expository by construction, so it suits this
   unusually well. Separates "learned the register" from "learned the content."
4. ~~bits-per-byte~~ -- ALREADY REPORTED by `report`.

**Run it OFFLINE after each arm finishes**, never during: applies uniformly to all 9 sweep runs, no
restart, no comparability break. (1) and (2) are the ones that would actually decide the A/B.

## 7i. Depth attention as a LoopSplit RESCUE, not a standalone feature (added 2026-07-28)

Full argument: [[depth-attention-rescues-loopsplit-hypothesis]]. Short version -- a looped block
applies the same function repeatedly, so its passes converge to a fixed point and later passes buy
nothing. Depth attention caches (K,V) across DEPTH and lets later passes attend over the accumulated
set, so pass 3 is no longer the same function as pass 1. It also addresses the Phase G/H finding
directly: a looped block relies on the residual stream as the sole carrier between passes, which is
exactly the "inject once and let computation carry it" mechanism measured to lose fidelity.

Nanbeige ships LoopSplit and depth attention TOGETHER, in one section of the reference, which is
corroboration rather than proof. **Check `_apply_depth_attention` against this hypothesis
specifically** -- whether their depth cache participates in the LOOPED block or only in the un-looped
head/tail decides whether this is what they built.

**Gated on the 3-arm sweep**, because two of three outcomes change the decision (B~=A: polish, and
would confound a clean result; B~=C: this becomes the main thread with a mechanistic rationale;
B between: obvious gap-closer). Cost is unchanged -- CPU+CUDA forward and backward plus a cross-layer
K/V cache that is not small at 16 executions.

This supersedes the earlier "depth attention: unclear benefit at this scale, park it" position, which
was formed before the fixed-point argument existed.

## 7j. Plateau detector stops runs that are still improving (added 2026-07-28)

Full detail: [[plateau-detector-fires-while-still-improving]]. Two independent arms stopped at the
IDENTICAL step 8586 with `status=plateaued`, while `val_nelbo` set a NEW BEST at every eval right up
to the stop (A: 2.1435 -> 2.1385 -> 2.1332; B: 2.2191 -> 2.2179 -> 2.2140).

Suspect the minimum-relative-improvement threshold: the last gains were 0.23-0.25% (A) and 0.05-0.18%
(B) per eval, so a threshold demanding >~0.5% reads steady learning as a plateau. Firing on two
different architectures at the same eval boundary points at a threshold/schedule interaction, not
anything data-driven. Start at the `min_rel` interpolation near `train_stage.cpp:394`, and check
whether `1d6772a` (epoch clock now scaled by --corpus-fraction) shifted the eval cadence relative to
whatever the threshold was tuned against -- that change landed immediately before this appeared.

**Impact on the in-flight sweep**: results stay usable as a MATCHED-BUDGET comparison (both arms
consumed exactly 1,969,422,336 tokens) but must NOT be described as converged.

**Fix options**: retune the threshold, or pin `--steps` for A/B work so the detector is out of the
experiment entirely -- for a controlled comparison the latter is arguably better regardless.

**Cheap to correct later**: every arm keeps checkpoints, so a truncated run can be RESUMED from its
stop point and carried to real convergence rather than rerun from scratch.

User decision 2026-07-28: leave the sweep running as-is, fix afterwards.

## 7k. LoopSplit seed-1 RESULT + the agreed plan (added 2026-07-28)

**First interpretable LoopSplit measurement.** Dense corpus (Cosmopedia, vocab 16508), fixed-length
windows, and a CONTROL arm -- so unlike the TinyStories negative, this one can be read.

| arm | executions | layers | val_nelbo | tokens |
|-----|-----------|--------|-----------|--------|
| A deep16    | 16 | 16 | **2.1332** | 1.97B |
| B loop10x6  | 16 | 10 | 2.2140 | 1.97B |
| C shallow10 | 10 | 10 | 2.2291 | 1.86B |

**B sits far closer to C than to A: looping recovered only ~16% of what six real layers give, for
+60% executions.** And 16% is an OVER-estimate -- C stopped ~6% short on tokens (7089 steps vs 8586),
so a matched-budget C would score better and shrink B's margin further.

Caveats: ONE seed (GQA noise ran 1.73x signal, and the B-C gap of 0.0151 is well inside that; the
A-B gap of 0.0808 is 5x larger and likelier real), and all three are matched-BUDGET not converged
(see 7j).

**Read**: at this scale looping does not meaningfully substitute for real layers. This is "outcome 2"
of the pre-registered framing, which promotes [[depth-attention-rescues-loopsplit-hypothesis]] from
backlog to main thread -- extra passes through identical weights bought almost nothing, exactly what
convergence-to-a-fixed-point predicts.

## AGREED PLAN (user decision 2026-07-28), in order

1. **Make training comparable first.** Fix 7j -- runs must either converge properly or use a pinned

   D should close most of the A-B gap that B alone could not.
3. **Then** the long multi-seed comparison across all four arms.
