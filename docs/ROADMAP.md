# Roadmap — from tiny fluency to small, composable agents

Scope note: this is a **capability/data/architecture roadmap** — what to train on and what to build
toward. It complements [WORKFLOW_ARCHITECTURE.md](WORKFLOW_ARCHITECTURE.md) (the CLI/build-tool
architecture) and [CONFIGURE_ARCHITECTURE.md](CONFIGURE_ARCHITECTURE.md) (how a corpus becomes a
compiled model), which stay as-is. Nothing here is committed engineering work; it is the map for where
the corpus/data-sourcing and architecture decisions are headed, so each near-term step can be judged
against a destination instead of picked in isolation.

## Thesis

A dense model's parameters pay for two different things that scale very differently: **world
knowledge** (facts, entities, dates, embedded trivia — compresses poorly, wants raw scale and broad
coverage) and **behavior** (grammar, coherence, instruction-following, reasoning steps, tool use,
conversational turn-taking — compresses well, and is mostly about *data density*, not parameter count).
[TinyStories](https://arxiv.org/abs/2305.07759) already proved the second half of that split inside
this project: a few-million-parameter model gets fluent and coherent on a synthetic corpus built to be
behavior-dense (simple vocabulary, strong narrative structure, no noise), at a scale that would produce
gibberish if trained on raw web text instead. [[tinystories-default-analysis-corpus]] is the existing
memory recording why this became the project's default smoke-test corpus.

FineWeb-Edu, by contrast, is knowledge-dense but comparatively behavior-sparse — filtered for
educational *quality*, not for teaching a model how to converse, decompose a task, or call a tool. It
is genuinely the right corpus for the "does capacity scale sensibly with a real, large, broad-coverage
corpus" question the Chinchilla sweep is answering, and stays parked for that reason (see
[[production-line-pivot-medium-model]]) — but it is the wrong corpus for the *next* capability this
roadmap targets.

**Working hypothesis to test, not an assumed conclusion:** if a model is a strong enough conversational
reasoner and tool-user, it doesn't need to *also* be a large enough dense store of world knowledge —
it can look facts up. That substitutes retrieval/tool-calls for parameters on the knowledge axis, and
leaves parameter budget free to spend entirely on the behavior axis, where this project's own tiny-model
evidence already suggests small buys a lot. The end state this roadmap is aimed at is not one model that
does everything, but a **small family of purpose-sized models** — a conversational front-end sized for
"talk and decide what to do next," dispatching to narrower specialists (a lookup/retrieval step, a coding
model, etc.) each sized for what *their* task actually needs, not for the union of everything.

## Corpus catalog, by capability axis

Each entry: what it is, why it's on-theme (behavior/reasoning-dense vs. knowledge-dense), rough scale,
and the licensing/format caveat to check before use. **Sizes and license terms below are from training
knowledge, not verified against the current source — confirm both before committing a corpus**, same
discipline as checking a memory's claims against live code before acting on them.

### A. Foundational fluency (done)
- **TinyStories** (Eldan & Li, 2023) — synthetic, GPT-generated short children's stories on a
  restricted ~1500-word vocabulary. Already the project's default corpus. Proved the thesis at the
  smallest scale: coherent fluency from a few million params when the *data*, not the model, carries
  the structure.

### B. Broader knowledge (in progress, parked)
- **FineWeb-Edu** — already integrated, 46GB, paused per [[production-line-pivot-medium-model]] until
  the TinyStories line is stable at the new sizes.
- **Cosmopedia** (HuggingFace, 2024) — synthetic textbook/blogpost-style content, generated by
  prompting a large model to *explain* concepts clearly rather than scraping the web. This is the
  closest existing large public dataset to the "understanding/abstraction-dense, not just
  knowledge-dense" category the project wants — it's what SmolLM2 trained on (the same SmolLM2 whose
  aspect ratio anchors `kAspectMax` in `autosize()`, a nice existing thread to pull). Worth a serious
  look as a FineWeb-Edu alternative or supplement once the knowledge-density axis is revisited.
- **SmolTalk** (HuggingFace) — the conversational SFT mix used for SmolLM2-Instruct; a ready-made
  multi-source blend rather than a single corpus. Good reference point for what a "balanced" mix looks
  like once this project has its own conversational stage working.

### C. Conversational competence (the explicit next step)
- **Dolly-15k** (Databricks) — ~15k real human-written instruction/response pairs, small, permissively
  licensed. The natural "TinyStories-sized" first conversational corpus: small enough to keep the
  fast-iteration property that made TinyStories useful as a smoke test, real (not synthetic) so there's
  no synthetic-data license ambiguity to check.
  - **Recommended starting point** for exactly that reason — same role Dolly plays for the field's own
    small-model work (Databricks explicitly positions it as a lightweight instruction-tuning set).
- **Alpaca / Alpaca-GPT4** — 52k single-turn instruction/response pairs, synthetic (generated via
  self-instruct against GPT-3/GPT-4). Slightly larger, still small, widely used as a first-instruction-
  tuning baseline in the literature, so results are comparable against known reference points.
- **OASST1 / OASST2** (OpenAssistant) — real, human-generated, multi-turn, tree-structured
  conversations, Apache-2.0. Multilingual; would need an English filter. The best available real (not
  synthetic) *multi-turn* set at a still-modest scale — the natural second step after single-turn
  Dolly/Alpaca once turn-structure representation exists (see Gaps, below).
- **UltraChat** (200k) — large-scale synthetic multi-turn dialogue, two LLM instances conversing across
  many topics/personas. Much bigger than the others here; a later-stage scale-up once the small
  conversational corpora validate the pipeline, not a first move.

### D. Reasoning density (structured problem-solving, chain-of-thought)
- **TinyGSM** — a direct sibling of TinyStories in spirit: GPT-3.5-generated synthetic grade-school math
  problems + worked Python solutions, built specifically to test whether small models can learn
  reasoning from a curated synthetic set rather than scale. The single closest existing "does the
  TinyStories trick work for reasoning" precedent in the literature — worth a look purely for the
  methodology, independent of whether the exact dataset is used.
- **GSM8K** — grade-school math word problems with human-written worked solutions, small, MIT-licensed,
  well-known reference point.
- **MetaMathQA** — larger synthetic augmentation of GSM8K/MATH-style problems via rephrasing, for scale
  once GSM8K's small size stops being enough signal.
- **SlimOrca / OpenOrca** — FLAN-style tasks with GPT-4-generated chain-of-thought explanations attached
  — bridges instruction-following and reasoning density in one set, useful once conversational + basic
  reasoning are both working and need combining.

### E. Tool use / agentic behavior (bridges toward the stretch goal)
- **Glaive function-calling v2** — synthetic, Apache-2.0, function/tool-call examples in a JSON-schema
  style. The most directly reusable existing set for teaching "call this tool with these arguments"
  behavior, and a manageable size.
- **Gorilla / APIBench** — API-calling correctness dataset (real API signatures, not just JSON shape).
- **ToolBench / ToolLLM** — larger multi-tool agentic call-trace data; a later scale-up once the basic
  tool-call shape is learned from Glaive-scale data.

### F. Code, and the final stretch goal (agentic C++ coding)
- **The Stack / The Stack v2** (BigCode) — large permissively-licensed code corpus, filterable by
  language; the natural source for a raw C++ pretraining slice.
- **CodeSearchNet** — function+docstring pairs; **C++ coverage is thin** (it's Python/Java/JS/Go/PHP/
  Ruby-centric) — flagged explicitly so this isn't assumed to cover the target language.
- **CodeAlpaca / Evol-Instruct-Code / Magicoder-style sets** — synthetic instruction-tuned code data,
  also Python-skewed in practice.
- **Competitive-programming corpora** (Codeforces-style problem+solution sets) — genuinely
  C++-heavy in practice (it's the dominant language in that community), and pairs naturally with a
  compile-and-run correctness signal, which is exactly the evaluation this stretch goal needs.
- **Gap worth naming directly: public C++-specific instruction/agentic-coding data is comparatively
  scarce** next to Python. A likely-necessary step is *this project's own source tree and development
  history* — commit messages, PR-style diffs, the design docs already in `docs/` — as a bootstrap
  corpus: small, genuinely C++, and (unusually) exactly matched to the kind of "make this specific,
  scoped change and explain why" behavior an agentic coding assistant needs. Self-hosting in the same
  spirit as a compiler that eventually compiles itself.

## Not classic MoE: discrete, purpose-sized experts

Worth being precise about the difference, since "MoE" already means something specific. Classic
Mixture-of-Experts is **one model**: a router picks, per token, which FFN sub-layer(s) to activate,
inside one forward pass, trained end-to-end, every expert co-resident in memory. It buys conditional
compute (more total parameters, same active compute per token) but every expert still shares the same
backbone width/depth and training run.

What's being proposed here is coarser and simpler: **fully separate models**, each independently sized
and independently trained, dispatched to at the query/subtask level rather than the token level — closer
to a small system of specialists than a single gated network. This maps directly onto infrastructure
this project already has, rather than requiring new kernel work:

- The Chinchilla sweep + `sub0llm models --metrics` comparison table (see
  [[model-identity-date-tag-and-comparison-table]]) already characterizes capability-vs-size across a
  family of independently-trained models on the same corpus. Extending that family across *different*
  corpora/tasks, and picking a right-sized model per task from the resulting table, is a small step from
  what's already built — not a new architecture.
- No shared-weight gating kernel is needed (`backend_cuda.cu` has no expert-routing GEMM today, and
  wouldn't need one under this design) — dispatch happens *outside* any single model's forward pass, at
  the orchestration layer.
- Each expert can be sized purely for its own task's difficulty: a small classifier-scale model for "does
  this need a tool call," a mid-size conversational model for the front door, a larger model reserved
  for the coding specialist — rather than one backbone sized for the hardest task and wasting capacity
  on the easy ones.

**New components this implies, none built yet — explicitly future work, not scoped:**
- **A router/dispatcher.** Can start as simple as a rule/keyword classifier before ever being a learned
  model — the smallest possible version of this is not itself a research project.
- **A conversational orchestrator** — likely the smallest general-purpose model in the family, whose job
  is talking to the user, decomposing the request, and delegating (to a lookup step, a specialist model,
  a tool call), rather than answering everything itself. This is the model the "conversational
  competence" corpus work (section C above) is actually training toward.
- **A task-success evaluation harness.** Every measurement this project has today (`report`'s NELBO/
  bits-per-byte, `autotemp`'s coherence grid) scores *language modeling quality*, not "did the tool call
  have correct arguments" or "did the generated code compile and pass its tests." Reasoning/tool-use/code
  stages each need a real success signal beyond perplexity before they're meaningfully evaluable at all
  — this is a bigger gap than it looks and should be scoped before Stage 2 below starts in earnest.

## Staged progression

Mirrors the project's own established methodology (small focused corpus → fast iteration → validate →
scale) rather than jumping straight to the end goal.

**Stage 0 — done.** Base language modeling: TinyStories fluency line (the current d128→d768 sweep) +
FineWeb-Edu knowledge-scale groundwork (paused). Chinchilla-sweep infra, the comparison table, and
autotemp coherence tuning are the reusable substrate every later stage builds on.

**Stage 1 — next, per this conversation.** Conversational competence on a small, focused corpus
(Dolly-15k-scale first, per section C). **Blocked on one concrete engineering gap before any
conversational corpus can be ingested at all:** the current pipeline is one flat token stream with only
document-boundary markers ([[eos-token-and-fixed-marker-scheme]]) — there is no representation yet for
turn boundaries or speaker roles (user vs. assistant). This needs a small, scoped design decision (most
likely: new fixed marker tokens in the same family as the existing `TOK_EOS`/doc-boundary scheme, not a
new tokenizer mechanism) before Dolly/Alpaca-scale data is usable. Scope that first.

**Stage 2 — reasoning density.** GSM8K/TinyGSM-style chain-of-thought data, layered on top of Stage 1's
conversational base. Needs the task-success eval harness (above) to actually be measurable — NELBO on
a math-reasoning corpus doesn't tell you if the arithmetic is right.

**Stage 3 — tool use.** Glaive-function-calling-scale data. Needs a minimal execution harness capable of
actually running a tool call (even a stub) during eval, so "correct tool, correct arguments" is a real
measured signal, not an inference from the text looking plausible.

**Stage 4 — stretch, final goal. Agentic C++ coding.** Needs: a curated (likely partly self-authored,
per the gap noted in section F) C++ corpus, a compile-and-test execution harness (the generated code
must actually build and pass tests to be scored — the largest new infrastructure investment on this
list), and plausibly the discrete-experts split actually implemented (a dedicated coding specialist,
orchestrated by the Stage 1 conversational front-end) rather than one model carrying every stage's
behavior at once.

## Open risks and honest caveats

- **Licensing.** Every dataset above needs its license re-checked at the point of actual use, not
  assumed from this document — I'm recalling terms from training knowledge, which can be stale or
  imprecise (e.g. exact CC/Apache/ODC variant, any non-commercial carve-outs, opt-out mechanisms like
  The Stack's).
- **Hardware budget.** This is a single 8GB laptop GPU. Every stage above should keep sizing decisions
  anchored to what's actually feasible here (matching how the d512/d768 sweep points were feasibility-
  checked via `memplan` before committing GPU time) — the stretch goal is explicitly "further down the
  road," not a near-term compute target.
- **Eval methodology is the real bottleneck, not data availability.** Stages 2-4 all need a
  success-scoring harness this project doesn't have yet; sourcing the corpora is the easy half of each
  of those stages.
- **C++-specific agentic data is genuinely scarce** industry-wide, not just an oversight in this
  catalog — the self-hosting bootstrap idea in section F is a real plan, not a placeholder, but it's
  untested at any scale yet.
